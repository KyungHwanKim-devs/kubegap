# Analysis procedure — how to read the snapshot and judge

This file is step 5 and step 6 of `SKILL.md`. Read it fully before opening any snapshot file, and follow every rule in it; it is not optional. From here on the work is **reading and judgment**, not Bash. Everything is a file under `$SNAP/`. Extract only the needed parts of JSON with `python3 -I - <<'EOF' … EOF` (the files are several MB). The file shapes are documented in the references below; sessions that did not know the shapes have failed by groping around, so they are written down.

- Per-file shapes are in [snapshot-files.md](snapshot-files.md) (inventory, findings-draft, diff, objects, metrics) and [summary-shape.md](summary-shape.md) (per-section keys of summary.json). **Open only the sections you need** — summary.json sections: inventory, events(+history), metrics, objects, recent_changes, conditions, webhooks, observability, controlplane, nodeos, k3s(+cluster.datastore), logs, tools, resources, scaling, traffic, resilience, storage, hygiene, security, tenancy, cost, run, and the component sections vpccni, coredns, kubeproxy, ebscsi, albctl, karpenterctl, kedactl, esoctl, argocdctl, ecr, stackhealth (prometheus, alertmanager, grafana, loki), flannel, local_path, metallb, certmanager. When a component is absent its section is `{"present": false}`.

## 5. Reading order

1. **`inventory.json`.** Understand what the cluster is: `cluster.platform`, `server_version`, `profile`, `nodes` (count, versions, OS, runtime, zones, capacity-type skew), `namespaces.prod_like`, `components_present`, `missing_families`, `stores` (Prometheus and Loki retention), for EKS `cluster.eks` (logging, endpoint, add-ons, support type), `node_access` (nodes not registered in SSM).
2. **`findings-draft.json`.** The code's first-pass status. `findings` is sorted by severity; each item has `id`, `status` (fail/warn), `severity_default`, `symptom_linked`, `target`, `evidence` (a list plus `instances` when several pods were merged), `source` (raw file path), `why`, `suggest`, `verify`, `cases`, `thresholds`. `check_results` has pass/fail counts per check and skip/error reasons; also `suppressed`, `expired_suppressions`, `severity_rules` (the rule text), `llm_checks` (type: llm, to be judged without a rule).
3. **`summary.json`.** Events (cumulative occurrences per Reason, first/last, top targets, Warning samples), metrics (per-query statistics and top 30), objects (restart leaders, Pending, waiting reasons such as CrashLoop, Failed pods, Deployments below availability, replicas 1, Services with no ready endpoint, node pressure), run record. **Note anything odd that is not in the first-pass status**: e.g. an `events.reasons` entry with over a thousand `UpdateFailed` occurrences, a pod in `restarts_top` with thousands of restarts, a dozen Evicted pods, `cardinality_top_metrics`.
4. **The previous snapshot and previous report.** The `a` path in `diff.json` is the previous snapshot. Read its `inventory.json`, `findings-draft.json`, `summary.json`, and its two report files if present: `report.md` (the Top N problems and their actions, to say what progressed) and `report-details.md` (section 1-1 adjustments = the previous run's final severities, section 7-6 tool notes = the numbering to continue). Snapshots written before the two-file format have `report.md` with everything inside and sometimes `report-short.md`/`report-daily.md`; read whichever exists. If there is no earlier snapshot of this mode, there is nothing to compare with.
5. **`diff.json`.** Object additions, removals and changes (which fields changed), first-pass new/resolved/changed and rename suspects, inventory changes, Warning Reason deltas, metric value changes. `findings.persisted` says how many consecutive earlier snapshots contained this finding (`runs`, max 11) — if 3 or more in a row and it is the kind fixed by hand every time (restarts, manual scaling, manual cleanup), use it as a Toil candidate in the report. Short intervals between runs inflate the count, so read it together with the `taken_at` spacing.

### Scope modifiers

With `--namespace <ns>`, in steps 2, 3 and 5 look only at that namespace's items plus cluster-level items (nodes, platform, absence). With `quick`, look only at the namespaces and workloads in `recent_changes` of `summary.json` (Deployments, StatefulSets and DaemonSets whose status.conditions were updated within the last 24 hours, and the targets of ScalingReplicaSet and SuccessfulCreate events), cross-checked against the change list in `diff.json`. With `focus <area>`, only that area's checks and related summary. With `explain <finding-id>`, read that one finding's `source` file, related objects, metrics and events to the end and write only the explanation (not a full report).

## 6. Review

6. **Open the raw file for every fail and warn.** Open what `source` points to (that resource in `objects/<kind>.json`, that series in `metrics/<id>.json`, that target's events in `events.json`) and decide whether the first-pass status is right, a false positive, or more serious. When one check has dozens of findings you need not open them all, but open two or three representative ones to confirm the pattern and judge the rest from the evidence numbers. List every opened file path in report section 7-4. Log findings (`logs.*` signatures, `observability.unclassified-errors`, `log-error-ratio-high`, `unstructured-logs`) have no raw file to open: the component logs were aggregated into `summary.logs` and deleted after summarize (`logs/pods/REMOVED.txt`). Their evidence is the signature count, the masked sample lines and the file names in `summary.logs`; do not look for the log files. ConfigMaps in `objects/configmaps.json` carry `{len, shape}` instead of values, except the configuration keys kubegap parses; a `kubegap_scrub.secret_like_keys` list is the evidence for `security.plaintext-configmap-secret`.
7. **Compare anomalies not in the first-pass status (the notes from step 3) against the check definitions.** If a matching check exists, add a finding (id follows the same rule `<area>.<check>.<ns>/<resource>`); if not, write it in the report as an "unclassified finding" and mark it as a new-check candidate. E.g. an ExternalSecret with a very high `UpdateFailed` count when no check covers it is an unclassified finding.
8. **`type: llm` checks and correlation.** The only llm check today is `tenancy.noisy-neighbor` — its material is `summary.tenancy.noisy` (node-saturated minutes, dominant namespace, bursting tenants, prod throttling); if `nodes_saturated_7d` is empty, conclude "no room for neighbor impact in these 7 days". Beyond that, check whether one namespace's CPU spike overlaps another's latency, and whether recent deployments (changes in `diff.json`, `ScalingReplicaSet` events) overlap increases in 5xx or restarts. Without evidence write "insufficient evidence" and do not assert.
9. **Reconcile conflicting findings.** E.g. node request over-provisioning (lower requests) and CPU throttling (remove limits) on the same workload: remove the limit first, cut requests only after reviewing the 7-day p95. OOMKilled and no memory limit in the same namespace: not "drop the limit" but "set it from the p95".
10. **Apply the severity rules (`findings-draft.severity_rules`).** ① If `symptom_linked` and a real symptom (5xx, restart surge, Evicted, latency) is visible in the summary or events, raise one level. ② If something marked "resolved" in the previous report reappears, mark it "recurred" and raise one level; but if it is in `diff.json.findings.rename_suspects`, suspect a rename and do not treat it as recurrence. ③ No SLO, no symptom alert, no backup, N+1 not met are critical regardless of profile. ④ Profile context: under the lab profile, a 1–3 node cluster, "multi-AZ" items and "no HPA" (`scaling.no-hpa-serving-prod`) are info or lower. ⑤ When you overturn the first-pass status (two or more levels, or fail→pass), write the reason on that item.

### A finding that disappears after a rubric version change is not a defect

If a finding from the previous report is missing now and `rubric_version` went up, first read that check's `why` (it may carry a verdict-change note). If the change is intended there, do not record it as a "defect" in the tool notes (7-6); classify it under section 3 as a "criteria change". (`SKILL.md` section 6 states the same rule.)

### Read-only commands outside the snapshot

When something essential to the judgment is not in the snapshot, you **may read more with read-only commands** (e.g. `aws dlm get-lifecycle-policies`, `aws backup list-backup-plans`, Alertmanager routes). Three conditions. ① Read only (the forbidden list in `SKILL.md` section 9 applies unchanged). ② Save the output as `$SNAP/extra/<name>.txt` and record it with the command in appendix 7-4 as "read outside the snapshot" (reproducibility). ③ If port-forwarding is needed, use `lib/portfwd.PortForward` via `python3 -c` or a background run; do not block the foreground with a `sleep` loop (some hosts refuse or time out on it). If the same command is needed again on the next run, it is a candidate to promote into a collector (`collect.yaml`); note it in report section 7-6 "tool notes".

### Severity guidance (apply as written)

Page on symptoms, put causes on dashboards. Are the 4 golden signals (latency, traffic, errors, saturation) measured per service? Without an SLO there is no definition of "normal". Retries amplify outages. Does everything come back after losing one node? Repeated manual actions are automation candidates. Change is the trigger of incidents. Recurrence is the most expensive. A system you cannot understand cannot be trusted.

### Values that collection itself disturbed

collect sends about a hundred object LISTs and a hundred PromQL queries over 5–7 minutes. If `controlplane.apiserver-latency` (LIST p99), `apiserver-5xx` or Prometheus throttling overlaps the collection time (including the previous snapshot's `taken_at`), write "measured during collection (likely includes kubegap itself)" and do not count it as user impact. (`SKILL.md` section 9 lists this too.)

When the review is complete, return to `SKILL.md` section 7 and read `report-writing.md` before writing anything.


## Daily mode

Read in the same order, but stop at what the daily report needs: `diff.json` (new, resolved, recurred findings; changed objects; new Warning events), the `fail` findings with default severity critical or high, and the raw files behind those only. Skip the per-area deep reading (steps 3 and 5) unless one of the three problems you will write needs it. `findings-draft.json` `checks.by_status["not-collected"]` is the number of checks the daily run cannot judge; `summary.collection.mode` confirms the mode and `summary.collection.mode_skipped_steps` the steps. Areas that are mostly not collected in daily mode: node OS, control-plane logs (EKS), ECR, cost, k3s node internals, flannel and local-path node data.
