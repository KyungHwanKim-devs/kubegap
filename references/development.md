# Development reference: the mechanics behind the contributing rules

The procedure for adding a check, the commands, the pull request rules and the review checklist are in [`CONTRIBUTING.md`](../CONTRIBUTING.md); this file holds what those rules rest on, such as what the regression harness compares, what `modes:` does, how tools are pinned, where each helper lives and how the layers may import each other. A report session does not do this work (SKILL.md section 9); it belongs to a development session.

**When you add or edit a check, write its `test:` block at the same time and run `$KUBEGAP/scripts/kubegap selftest`.** A check's fail path only runs when a cluster is actually in that state, so running against a couple of real clusters does not catch key typos or type errors in the expression (they surface as `status: error` on the day of an incident). When `test.cases` contains fake fail, warn and pass inputs, selftest builds a temporary snapshot, really runs `evaluate_check`, and verifies the expected status, evidence sentence and target. Follow the shape of an existing check's `test:` block. When the expression compares against today's date (`days_until`, `k8s_eol`), set `today: "YYYY-MM-DD"` in each case's inventory so the expected verdict does not change as the calendar moves; `platform.k8s-version-eol` is the example. Every check has a `test:` block. Passing `--snapshot <snapshot folder>` with the latest snapshot of each cluster compares the keys referenced by summary-type check expressions against the real summary.json (fake inputs use the same keys as the check expression, so a key rename in a summary module is caught only by this comparison). The work is done only at 0 failures and 0 mismatches.

**The end-to-end regression test (`tests/test_regress.py`, #145).** `tests/fixtures/snapshot-<name>/` holds one committed `full` snapshot per reference cluster (`k3s`, `eks`), made from a real run by `scripts/make-fixture.py` (inputs only; the fields no reader uses trimmed, names replaced through a private map, the trims verified against the source run so no check changes its verdict; under 2 MB compressed each). `lib/commands/regress.py` copies a fixture to a temporary context folder (summarize deletes `logs/pods/*.log`, appends run.log notes and writes `events-history.json` and `history.csv` next to the snapshot, so the fixture itself is never run on), runs summarize → evaluate → render in both languages and compares summary.json, the check results and findings, and report-details.md with `tests/fixtures/expected/<variant>/`, after replacing the snapshot path, `generated_at` and the kubegap version. The `-degraded` variant of each fixture takes inputs away first (a forbidden List, no Prometheus, no node access, every AWS call refused, a kind the account may not list) and the test checks that every check whose status changes is skipped with a reason and that the loss reaches summary.json and section 7-1 (a check that still judges the emptied section and passes is #141's empty-result policy; the two expectations side by side show which). `references/summary-shape.md` is compared with the summaries the fixtures produce: every heading is a key, every key has a heading, every documented first-level key exists in at least one fixture (deeper keys are not parsed from the prose; a moved nested key is caught by the summary.json expectation). When a change to a summary module, a check or the renderer is meant to change the output, run `scripts/kubegap regress --update` and commit the new expectation with the change; the diff of `tests/fixtures/expected/` is the review material. A rubric version bump alone changes the expectation too (the version is printed), so bump and update in the same commit. To add a cluster: `scripts/make-fixture.py <snapshot> tests/fixtures/snapshot-<name> --map <your map>` (map format: the header of `scripts/scrub-sample.py`), read the verify lines it prints, then `--update`.

**Collection units and modes.** A snapshot is collected in `daily` (default) or `full` mode (`scripts/kubegap collect --mode`, config key `mode`). What a mode reads is declared in one file, `collectors/units.yaml`: a unit says what it reads, what of it is written, what is dropped in memory, how sensitive it is and which modes collect it; a mode is the list of units that name it. Every step of a `collect.yaml` names its unit (`unit:`), and a step of a unit the mode leaves out is recorded as skipped by the mode. A check that cannot be judged without a unit names it (`needs: [node-os]`) and is reported as `not-collected` in a snapshot whose mode does not collect it, instead of being evaluated on data that is not there. No step and no check lists modes, and no code asks which mode it is: it asks `units.collected(mode or snapshot, unit)` (`lib/foundations/units.py`). Two units add nothing to what is read and decide what is kept of it: without `app-settings` the scrub keeps no command, args, literal environment value or ConfigMap key outside the system namespaces (`lib/foundations/scrub.py`; what a check asks of a command, whether it is a shell script or only sleeps, is recorded before the command goes), and without `component-log-samples` no log text is kept. The daily run collects units of low sensitivity only (`tests/test_units.py`). Whether a check needs a unit is found by data, not by reading: `tests/test_regress.py` turns each committed full fixture into what a daily run would have written (`regress.as_mode`) and fails when a check that still judges gives another verdict than on the full fixture; such a check gets the `needs` line, or, when it keeps judging on the part it still has, a line in `PARTIAL_IN_DAILY` that says what it loses. Snapshots of different modes are never compared with each other (`paths.previous_snapshot` stays within one mode).

**Pinned tools.** `lib/commands/tools.py` pins every download to a version and a sha256 per platform; `kubegap setup --check-tool-updates` prints the next pin's material. The aws zip carries the publisher's OpenPGP signature as well (`deploy/aws-cli-public-key.asc`, verified in a temporary keyring when gpg exists). krr is a virtualenv from `deploy/krr-requirements.txt`, every package with a sha256 per file; to move krr to a new tag run `kubegap setup --check-tool-updates krr` with a supported Python on the machine, write its output to that file and change the tag in `venv.pip`. (#88, #108)

**Before adding a helper, look for it: every small job has one home (#140, #150).** Version strings are read by `lib/foundations/versions.py` (major, minor, the next minor, a minor gap, the semver triple of an image tag with `image_version`), Kubernetes quantities and the small number helpers by `lib/foundations/quantity.py` (`parse` for `500m`/`2Gi` into cores or bytes with `MIB` to divide by, `to_float`, `to_int`, `rounded`), Prometheus text by `lib/foundations/promtext.py`, pod metric names by `lib/foundations/podmetrics.py`, Go durations by `lib/foundations/durations.py`, YAML by `lib/foundations/yamlite.py` (`load`, or `mapping_value` for text the parser rejects), Alertmanager's configuration by `lib/foundations/amconfig.py`, the node script's `### section` text and the kernel `oom-kill:` line by `lib/foundations/nodetext.py`, klog lines by `lib/foundations/logtext.py` (`normalize_message`), and snapshot files by `lib/foundations/snapshot.py`: objects (`objects`, `items`, `parse_ts`, `taken_at`, `event_count`) the Prometheus result files (`metric_doc`, `metric_result`, `metric_rows`, `metric_by`, `metric_value`, `metric_sample` for the evaluator, which lets a rule judge a NaN itself, `metric_scalar`, `metric_sum`, `series_present`; only snapshot.py reads `metrics/*.json` and only prom.py writes them) and the node script's output (`node_os_text`). What a workload is, read from the objects alone, is `lib/foundations/workload.py`: `workload_of` (the workload name from a pod name), `key` (`namespace/kind/name`), `is_db_like`, `image_repo`, `mounts_pvc`, `selector_matches`, `eligible_nodes`. Markdown table cells are `lib/output/render.cell` and `lib/output/render.table`, which `lib/output/writer` uses too. A private `_q`, `_ver`, `_r`, `_rows`, `_metric_rows` or `_wl` in a summary module is the duplicate the review asks about: `tests/test_helper_homes.py` fails on a private helper with the same body in two modules, on a function named after a job that has a home (its `HOMED` table says which), and on a unit table, an image-tag regular expression or a `metrics/<query>.json` path written outside the home; `tests/test_versions.py` fails on a second version regex.

**The layers of lib/ are its packages, and an import may only go down (#149, #151).** `lib/` has six packages, one per layer, bottom to top: **foundations** (`lib/foundations/`: standard-library helpers and the loaders of the data files, `paths`, `yamlite`, `snapshot`, `shell`, `runlog`, `config`, `versions`, `quantity`, `durations`, `promtext`, `nodetext`, `logtext`, `podmetrics`, `metricnames`, `signatures`, `rubric`, `components`, `scrub`, `mask`, `http`, `amconfig`, `lastapplied`, `workload`; they know neither the cluster nor the checks), **collection** (`lib/collection/`: what touches the cluster, AWS, the nodes or Prometheus and writes the snapshot: `kube`, `aws`, `discover`, `collect`, `prom`, `monitoring`, `node`, `nodecommands`, `portfwd`, `cwlogs`, `cwmetrics`, `albmetrics`, `logsinks`), **summaries** (`lib/summaries/`: one module per section of summary.json, each reading snapshot files; `summarize` runs them), **judgement** (`lib/judgement/`: `evaluate`, which reads summary.json and the metric files and judges the checks), **output** (`lib/output/`: `render`, `diff`, `verified`, `writer`, the result in a form a person reads) and **commands** (`lib/commands/`: the bodies of `scripts/kubegap` sub-commands, `setup`, `firstrun`, `configedit`, `prune`, `regress`, `selftest`, `tools`). A layer hands its work to the next one as files, never as an import: collection imports the foundations and its own package; a summary module imports the foundations only, never a sibling, never `evaluate` or `render`; `evaluate` imports the foundations and reads the summaries' output; output imports the foundations and its own package and reads the judgement's output; commands may import anything. The one exception is `summarize`, the entry point of the summaries package, which runs every section module by name. A module imports another package as `from ..foundations.snapshot import objects` and its own as `from .events import TRACKED`; outside `lib/` (the CLI, the tests) the path is `lib.<layer>.<module>`. A module too large for one file is a sub-package (`lib/summaries/resilience/`, `lib/summaries/hygiene/`, `lib/collection/collect/`, `lib/judgement/evaluate/`): its `__init__.py` is the module (the entry point and what it shares with its parts, such as the `Ctx` of loaded objects), the other files are its parts split by responsibility (`resilience/capacity.py` is the N+1 model, `collect/tool_steps.py` the tool step, `evaluate/types.py` the check-type handlers), a part imports the foundations and may import another part but never in a cycle and never the `__init__`, and parts count as their module for the layer rule; a part is imported from its own path (`from lib.collection.collect.tool_steps import run_tool_step`), the `__init__` re-exports nothing it does not use itself. Data lives next to the code that interprets it and is not code: `collectors/*/*.yaml`, `rubric/`, `signatures/` and `references/*.yaml` are read by the foundations loaders; a fact that changes with a version goes into one of those files, not into a module. `tests/test_boundaries.py` reads the layer of every module from its folder and the `import` statements of every module (inside functions too, and summarize's by-name dispatch): a module at the top of `lib/` fails (it belongs in a layer), an import against the rule fails, and a known one is listed in `EXCEPTIONS` with its date and the issue that removes it (none today: since #151 the three summaries that computed part of another section, security from hygiene's polaris, traffic from security's NetworkPolicy enforcement, observability from traffic's ALB-covered Services, receive it from `summarize` as an argument). An exception row whose import is gone fails the test, so the list cannot outlive the debt. `lib/commands/tools.py` (900 lines) stays one file because the pinned tools are one responsibility; its header says so.

**Facts about other software come from its source, at the version kubegap pins or supports.** What a tool prints, which flag or environment variable it reads, what a metric is called, what an API field means: before a check, a collector step or a sentence in the docs relies on it, find the line in the project's source at the pinned tag (`curl raw.githubusercontent.com/<repo>/<tag>/<path>` or `gh api`) and cite it as `file:line@version` in the code comment, the test or the PR. `--help` output, the behaviour seen on one cluster and memory of how such tools usually work are observations or guesses, and each has already produced a wrong sentence in this repository (polaris and `--kubeconfig`, #104). Follow a dependency into its own source when the behaviour lives there (controller-runtime for polaris and pluto, kubernetes-python for krr). Report what was read in source and what was only observed as two different things. The facts already verified are listed in `references/sources.md`, one row per fact with the kubegap location and the `file:line@version`; `tests/test_sources.py` checks the rows, requires a `source:` line on every `type: tool` and `type: pod-metrics` collection step, and a `source:` list on every PromQL query of `collectors/*/metrics.yaml` that reads a node-exporter, cAdvisor, kubelet, kube-state-metrics, apiserver, CoreDNS, kube-proxy, EBS CSI, kubelet volume, client-go, Prometheus, Alertmanager, Loki, promtail, Fluent Bit, KEDA or ingress-controller series, or a series Prometheus writes itself (`up`, `scrape_*`, `ALERTS`), one entry per name with the definition's `file:line@tag` at every version read (a `{__name__=~...}` selector that spells a cited family needs an entry the pattern matches; name every name it matches). A fact that changes with the version of the other software, such as a metric name, goes into a data file next to the step (`collectors/<area>/pod-metrics.yaml`: the spellings newest first, `since`/`before` bounds, a `source:` per spelling) and the parser asks `lib/foundations/podmetrics.py` for a logical key, so supporting a new release is one YAML entry with its citation and never a parser edit; a fixture written from the source stands in for a version no cluster at hand runs.

**What a rule needs before it can judge.** `rule.needs` is an expression evaluated per target before `expr`; when it is false the target is not judged and the check counts it as skipped with `rule.needs_reason` (a short noun phrase such as `metrics not read`, `kubelet not read`, `acm not available`). A check whose targets all lack what it needs reports `skip`, never `pass`; a check where some targets lack it reports `done` with `skipped_reason`, and section 7-5 lists it under "judged in part". Write the availability of an input here, not as `item.get('available') and …` at the head of `expr`: that form evaluates to false and counts as a pass, which the report cannot tell from a healthy cluster (#114). `tests/test_degraded.py` fails on such a guard. A test case for the missing-input shape uses `expect: "skip"`.

**The golden-signal name lists are data with a source per name (#143).** `collectors/prometheus/golden-signal-names.yaml` holds the HTTP-server and saturation metric names (and name fragments) the two namespace queries match, each with the library that emits it and the `file:line@tag` where the name is set; the queries in `metrics.yaml` are the regexes the file builds and `tests/test_sources.py` compares them. To support a library, read where it names its metric, add the entry with the citation, rebuild the query text (the test prints the expected regex), and add the repository to `libraries` of `references/verified-versions.yaml`. A name no library defines stays out.

**Every version a fact was read at is in `references/verified-versions.yaml` (#146).** One entry per component: its repositories, every tag cited for them (`read`), what the two reference clusters run, the newest release read, the installation the queries assume and what happens outside it. README's "Verified against" table (both languages) is generated from it with `scripts/kubegap verified --markdown [--language ko]` and pasted between the `verified-table` markers; the report header compares the audited cluster's Kubernetes and store versions with the range (`lib/output/verified.range_note`). When you read a project at a new tag and cite it (`owner/repo path:line@tag`), add the tag to the component's `read`; a repository that is only a library read for a signature goes under `libraries`. `tests/test_verified_doc.py` fails on a tag or repository the file does not know and on a stale table. The scan covers `collectors/*/*.yaml`, `collectors/*/*.sh`, `signatures/`, `lib/*/*.py`, `rubric/*.yaml`, `deploy/`, `SKILL.md` and `references/sources.md`; a citation written as `, :41@tag` after a first one is attributed to the repository last named on the line, and in prose that can be wrong, so such a tag is only required to be one the file knows somewhere.

**Interfaces change without aliases, and the snapshot says which version wrote it (#147, #97).** The summary keys (`references/summary-shape.md`), the config keys (`lib/foundations/config.py` KNOWN_KEYS), the metric query ids and the snapshot files are interfaces a user's tooling may read. When one is renamed, removed or re-typed, the code knows the new form only: no alias, no old spelling served next to the new one, no deprecation period. What moves instead is a version and a sentence: a summary key, a query id or a check changes the rubric version (`rubric/version`, SKILL.md) and is named in the CHANGELOG with the old and the new spelling under Changed or Removed; a top-level snapshot file renamed or removed, or a key a reader requires, moves `paths.SCHEMA_VERSION`, which discovery writes as `schema` into inventory.json (summarize and evaluate copy it) and `snapshot.check_schema` compares at the two entrances a snapshot comes in by, the `scripts/kubegap` snapshot argument and `lib/commands/regress.stage`: a snapshot of another version is refused with both numbers and is collected again, never read. `kubegap diff` records the kubegap, schema, rubric and signature versions of both runs (`versions`) and the metric queries one side has and the other has not (`metrics_queries`), and report section 3 says when the two runs differ in version, so a renamed key or query reads as a difference of the tool, not of the cluster. Three readers look into neighbouring snapshots without the check and on purpose, because they read one field that no format change has touched: `diff.persisted_findings` (finding ids of up to ten earlier runs), `events.build_history` (kubectl events of every run in the context folder) and `kubegap mask` (the account id of the sibling inventory). `tests/test_shape_history.py` compares the working tree's `references/summary-shape.md` with the one of the last tagged release: a section or first-level key that disappeared must be named in the CHANGELOG since that release.

**An empty result is not a pass by itself (#141).** A `type: metric` check whose query returns no series asks lib/judgement/evaluate what the emptiness means: the names the query cites in its `source:` entries (lib/foundations/metricnames.py) are looked up in `metrics/series-present.json`, which collection writes with one `count by (__name__)` query per metrics.yaml (lib/collection/prom.record_series_present). A name with no series at all means not scraped, renamed or removed, and the check skips naming it; every name present means the situation did not occur, a pass counted as `empty` and listed in section 7-5. `rule.empty: skip` (with `empty_reason`) makes a check skip on any empty result; `rule.empty: pass` keeps the pass whatever the names say, for a counter that has no series until its first event (the kube-proxy iptables restore-failure counters since Kubernetes 1.33, which today are read through `summary.kubeproxy`, not by a metric check). A `type: summary` check never judges a section whose input was not read: the module writes the list or dict as `null` with a `skip_reason` on the parent when the whole section depends on one input (lib/judgement/evaluate skips with that reason), or a read flag on each row when rows exist but their measurement does not, and the check's `rule.needs` reads the flag (`needs_reason` says what was not read). A missing input is never `0`, `false` or `[]`: those are facts, and a check would pass on them. The degraded variants of `tests/test_regress.py` hold this: a check that loses a fail or warn when inputs are taken away must have skipped the targets it could not judge.

**Check fields and the warn-only form.** A check's `rule` has up to four parts: `expr` (true means fail), `warn_expr` (true means warn, evaluated only when `expr` is false or absent), and `threshold` / `warn_threshold` (numbers, or a mapping with `default` and the platforms or scales that differ, exposed to the expressions as `threshold` and `warn_threshold`). A check that should only ever warn writes `warn_expr` and **omits `expr`** (a rule without `expr` never fails; do not write `expr: "False"`). `absence` and `llm` checks need no `rule`; every other type needs `expr` or `warn_expr`, otherwise `load_checks` reports a validation error. For every `metric` check with a numeric fail threshold, add one test case whose value is **exactly the threshold** (the `>=` versus `>` boundary); selftest prints a note for metric checks that still lack one.

**Public cases and measurements.** `cases` lists published incident write-ups whose root cause is the condition the check detects, each `{ who: Company YEAR, url: https://… }`; the report cites only these as cases. What you measured on your own clusters while writing the check (a value, a pass, an outage you saw) goes into `measured`, a text field, never into `why` or `notes`. The report does not show it; it is a note for whoever changes the check. `tests/test_cases.py` fails when `why` or `notes` carry a measurement.

When you change `collectors/*/checks.yaml`, `collectors/core/metrics.yaml` , `rubric/platforms/*.yaml` or `rubric/scales.yaml`, bump `rubric/version`. When you change signatures (`signatures/catalog.yaml`, `collectors/*/signatures.yaml`), bump `signatures/version` (first edition = 1.0.0). Both versions are stamped in the report header and in `history.csv`, so a change in finding counts can be attributed to either a cluster change or a criteria change. Both started at 0.1.0.
