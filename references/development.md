# Changing checks and the rubric (development reference)

Moved here from SKILL.md section 10. A report session does not do this work (section 9) — it belongs to a development session.

**When you add or edit a check, write its `test:` block at the same time and run `$KUBEGAP/scripts/kubegap selftest`.** A check's fail path only runs when a cluster is actually in that state, so running against a couple of real clusters does not catch key typos or type errors in the expression (they surface as `status: error` on the day of an incident). When `test.cases` contains fake fail, warn and pass inputs, selftest builds a temporary snapshot, really runs `evaluate_check`, and verifies the expected status, evidence sentence and target. Follow the shape of an existing check's `test:` block. Every check has a `test:` block. Passing `--snapshot <snapshot folder>` with the latest snapshot of each cluster compares the keys referenced by summary-type check expressions against the real summary.json (fake inputs use the same keys as the check expression, so a key rename in a summary module is caught only by this comparison). The work is done only at 0 failures and 0 mismatches.

**Collection modes and the `modes:` field.** A snapshot is collected in `daily` (default) or `full` mode (`scripts/kubegap collect --mode`, config key `mode`). A step in `collect.yaml` with `modes: [full]` is skipped by the daily run (today: node scripts, CloudWatch Logs Insights and CloudWatch metrics, cost and pricing, ECR, service quotas, and the krr/polaris/pluto/kubent/helm tools); a check in `checks.yaml` with `modes: [full]` is reported as `not-collected` in a daily snapshot instead of being evaluated on missing inputs. Keep the two in step: when you mark a step `full`, mark every check that reads its output (directly or through a summary section) `full` too; the way to find them is to copy a full snapshot, delete the step's output files, re-run summarize and evaluate, and tag every check whose status or counts changed. Snapshots of different modes are never compared with each other (`paths.previous_snapshot` stays within one mode).

**Check fields and the warn-only form.** A check's `rule` has up to four parts: `expr` (true means fail), `warn_expr` (true means warn, evaluated only when `expr` is false or absent), and `threshold` / `warn_threshold` (numbers, or a mapping per profile, exposed to the expressions as `threshold` and `warn_threshold`). A check that should only ever warn writes `warn_expr` and **omits `expr`** (a rule without `expr` never fails; do not write `expr: "False"`). `absence` and `llm` checks need no `rule`; every other type needs `expr` or `warn_expr`, otherwise `load_checks` reports a validation error. For every `metric` check with a numeric fail threshold, add one test case whose value is **exactly the threshold** (the `>=` versus `>` boundary); selftest prints a note for metric checks that still lack one.

When you change `collectors/*/checks.yaml`, `collectors/core/metrics.yaml` or `rubric/profiles/*.yaml`, bump `rubric/version`. When you change signatures (`signatures/catalog.yaml`, `collectors/*/signatures.yaml`), bump `signatures/version` (first edition = 1.0.0). Both versions are stamped in the report header and in `history.csv`, so a change in finding counts can be attributed to either a cluster change or a criteria change. Both started at 0.1.0.
