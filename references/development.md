# Changing checks and the rubric (development reference)

Moved here from SKILL.md section 10. A report session does not do this work (section 9) — it belongs to a development session.

**When you add or edit a check, write its `test:` block at the same time and run `$KUBEGAP/scripts/kubegap selftest`.** A check's fail path only runs when a cluster is actually in that state, so running against a couple of real clusters does not catch key typos or type errors in the expression (they surface as `status: error` on the day of an incident). When `test.cases` contains fake fail, warn and pass inputs, selftest builds a temporary snapshot, really runs `evaluate_check`, and verifies the expected status, evidence sentence and target. Follow the shape of an existing check's `test:` block. When the expression compares against today's date (`days_until`, `k8s_eol`), set `today: "YYYY-MM-DD"` in each case's inventory so the expected verdict does not change as the calendar moves; `platform.k8s-version-eol` is the example. Every check has a `test:` block. Passing `--snapshot <snapshot folder>` with the latest snapshot of each cluster compares the keys referenced by summary-type check expressions against the real summary.json (fake inputs use the same keys as the check expression, so a key rename in a summary module is caught only by this comparison). The work is done only at 0 failures and 0 mismatches.

**The end-to-end regression test (`tests/test_regress.py`, #145).** `tests/fixtures/snapshot-<name>/` holds one committed `full` snapshot per reference cluster (`k3s`, `eks`), made from a real run by `scripts/make-fixture.py` (inputs only; the fields no reader uses trimmed, names replaced through a private map, the trims verified against the source run so no check changes its verdict; under 2 MB compressed each). `lib/regress.py` copies a fixture to a temporary context folder (summarize deletes `logs/pods/*.log`, appends run.log notes and writes `events-history.json` and `history.csv` next to the snapshot, so the fixture itself is never run on), runs summarize → evaluate → render in both languages and compares summary.json, the check results and findings, and report-details.md with `tests/fixtures/expected/<variant>/`, after replacing the snapshot path, `generated_at` and the kubegap version. The `-degraded` variant of each fixture takes inputs away first (a forbidden List, no Prometheus, no node access, every AWS call refused, a kind the account may not list) and the test checks that every check whose status changes is skipped with a reason and that the loss reaches summary.json and section 7-1 (a check that still judges the emptied section and passes is #141's empty-result policy; the two expectations side by side show which). `references/summary-shape.md` is compared with the summaries the fixtures produce: every heading is a key, every key has a heading, every documented first-level key exists in at least one fixture (deeper keys are not parsed from the prose; a moved nested key is caught by the summary.json expectation). When a change to a summary module, a check or the renderer is meant to change the output, run `scripts/kubegap regress --update` and commit the new expectation with the change; the diff of `tests/fixtures/expected/` is the review material. A rubric version bump alone changes the expectation too (the version is printed), so bump and update in the same commit. To add a cluster: `scripts/make-fixture.py <snapshot> tests/fixtures/snapshot-<name> --map <your map>` (map format: the header of `scripts/scrub-sample.py`), read the verify lines it prints, then `--update`.

**Collection modes and the `modes:` field.** A snapshot is collected in `daily` (default) or `full` mode (`scripts/kubegap collect --mode`, config key `mode`). A step in `collect.yaml` with `modes: [full]` is skipped by the daily run (today: node scripts, CloudWatch Logs Insights and CloudWatch metrics, cost and pricing, ECR, service quotas, and the krr/polaris/pluto/kubent/helm tools); a check in `checks.yaml` with `modes: [full]` is reported as `not-collected` in a daily snapshot instead of being evaluated on missing inputs. Keep the two in step: when you mark a step `full`, mark every check that reads its output (directly or through a summary section) `full` too; the way to find them is to copy a full snapshot, delete the step's output files, re-run summarize and evaluate, and tag every check whose status or counts changed. Snapshots of different modes are never compared with each other (`paths.previous_snapshot` stays within one mode).

**Pinned tools.** `lib/tools.py` pins every download to a version and a sha256 per platform; `kubegap setup --check-tool-updates` prints the next pin's material. The aws zip carries the publisher's OpenPGP signature as well (`deploy/aws-cli-public-key.asc`, verified in a temporary keyring when gpg exists). krr is a virtualenv from `deploy/krr-requirements.txt`, every package with a sha256 per file; to move krr to a new tag run `kubegap setup --check-tool-updates krr` with a supported Python on the machine, write its output to that file and change the tag in `venv.pip`. (#88, #108)

**Before adding a helper, look for it.** Version strings are read by `lib/versions.py` (major, minor, the next minor, a minor gap), Prometheus text by `lib/promtext.py`, pod metric names by `lib/podmetrics.py`, YAML by `lib/yamlite.py` (`load`, or `mapping_value` for text the parser rejects), Alertmanager's configuration by `lib/amconfig.py`, snapshot files by `lib/snapshot.py`. A private `_minor` or `_parse_*` in a summary module is the duplicate the review asks about; `tests/test_versions.py` fails on a second version regex. (#140, #150)

**Facts about other software come from its source, at the version kubegap pins or supports.** What a tool prints, which flag or environment variable it reads, what a metric is called, what an API field means: before a check, a collector step or a sentence in the docs relies on it, find the line in the project's source at the pinned tag (`curl raw.githubusercontent.com/<repo>/<tag>/<path>` or `gh api`) and cite it as `file:line@version` in the code comment, the test or the PR. `--help` output, the behaviour seen on one cluster and memory of how such tools usually work are observations or guesses, and each has already produced a wrong sentence in this repository (polaris and `--kubeconfig`, #104). Follow a dependency into its own source when the behaviour lives there (controller-runtime for polaris and pluto, kubernetes-python for krr). Report what was read in source and what was only observed as two different things. The facts already verified are listed in `references/sources.md`, one row per fact with the kubegap location and the `file:line@version`; `tests/test_sources.py` checks the rows, requires a `source:` line on every `type: tool` and `type: pod-metrics` collection step, and a `source:` list on every PromQL query of `collectors/*/metrics.yaml` that reads a node-exporter, cAdvisor, kubelet, kube-state-metrics, apiserver, CoreDNS, kube-proxy, EBS CSI, kubelet volume, client-go, Prometheus, Alertmanager, Loki, promtail, Fluent Bit, KEDA or ingress-controller series, or a series Prometheus writes itself (`up`, `scrape_*`, `ALERTS`), one entry per name with the definition's `file:line@tag` at every version read (a `{__name__=~...}` selector that spells a cited family needs an entry the pattern matches; name every name it matches). A fact that changes with the version of the other software, such as a metric name, goes into a data file next to the step (`collectors/<area>/pod-metrics.yaml`: the spellings newest first, `since`/`before` bounds, a `source:` per spelling) and the parser asks `lib/podmetrics.py` for a logical key, so supporting a new release is one YAML entry with its citation and never a parser edit; a fixture written from the source stands in for a version no cluster at hand runs.

**What a rule needs before it can judge.** `rule.needs` is an expression evaluated per target before `expr`; when it is false the target is not judged and the check counts it as skipped with `rule.needs_reason` (a short noun phrase such as `metrics not read`, `kubelet not read`, `acm not available`). A check whose targets all lack what it needs reports `skip`, never `pass`; a check where some targets lack it reports `done` with `skipped_reason`, and section 7-5 lists it under "judged in part". Write the availability of an input here, not as `item.get('available') and …` at the head of `expr`: that form evaluates to false and counts as a pass, which the report cannot tell from a healthy cluster (#114). `tests/test_degraded.py` fails on such a guard. A test case for the missing-input shape uses `expect: "skip"`.

**An empty result is not a pass by itself (#141).** A `type: metric` check whose query returns no series asks lib/evaluate what the emptiness means: the names the query cites in its `source:` entries (lib/metricnames.py) are looked up in `metrics/series-present.json`, which collection writes with one `count by (__name__)` query per metrics.yaml (lib/prom.record_series_present). A name with no series at all means not scraped, renamed or removed, and the check skips naming it; every name present means the situation did not occur, a pass counted as `empty` and listed in section 7-5. `rule.empty: skip` (with `empty_reason`) makes a check skip on any empty result; `rule.empty: pass` keeps the pass whatever the names say, for a counter that has no series until its first event (the kube-proxy iptables restore-failure counters since Kubernetes 1.33, which today are read through `summary.kubeproxy`, not by a metric check). A `type: summary` check never judges a section whose input was not read: the module writes the list or dict as `null` with a `skip_reason` on the parent when the whole section depends on one input (lib/evaluate skips with that reason), or a read flag on each row when rows exist but their measurement does not, and the check's `rule.needs` reads the flag (`needs_reason` says what was not read). A missing input is never `0`, `false` or `[]`: those are facts, and a check would pass on them. The degraded variants of `tests/test_regress.py` hold this: a check that loses a fail or warn when inputs are taken away must have skipped the targets it could not judge.

**Check fields and the warn-only form.** A check's `rule` has up to four parts: `expr` (true means fail), `warn_expr` (true means warn, evaluated only when `expr` is false or absent), and `threshold` / `warn_threshold` (numbers, or a mapping per profile, exposed to the expressions as `threshold` and `warn_threshold`). A check that should only ever warn writes `warn_expr` and **omits `expr`** (a rule without `expr` never fails; do not write `expr: "False"`). `absence` and `llm` checks need no `rule`; every other type needs `expr` or `warn_expr`, otherwise `load_checks` reports a validation error. For every `metric` check with a numeric fail threshold, add one test case whose value is **exactly the threshold** (the `>=` versus `>` boundary); selftest prints a note for metric checks that still lack one.

**Public cases and measurements.** `cases` lists published incident write-ups whose root cause is the condition the check detects, each `{ who: Company YEAR, url: https://… }`; the report cites only these as cases. What you measured on your own clusters while writing the check (a value, a pass, an outage you saw) goes into `measured`, a text field, never into `why` or `notes`. The report does not show it; it is a note for whoever changes the check. `tests/test_cases.py` fails when `why` or `notes` carry a measurement.

When you change `collectors/*/checks.yaml`, `collectors/core/metrics.yaml` or `rubric/profiles/*.yaml`, bump `rubric/version`. When you change signatures (`signatures/catalog.yaml`, `collectors/*/signatures.yaml`), bump `signatures/version` (first edition = 1.0.0). Both versions are stamped in the report header and in `history.csv`, so a change in finding counts can be attributed to either a cluster change or a criteria change. Both started at 0.1.0.
