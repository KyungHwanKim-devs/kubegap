# Permissions, one by one

What each grant in [`deploy/permissions/clusterrole.yaml`](../deploy/permissions/clusterrole.yaml) and [`deploy/permissions/iam-policy.json`](../deploy/permissions/iam-policy.json) is used for: the collection step or library code that calls it, the mode in which that runs, the checks that need the result, and what happens when the grant is missing. A grant you remove costs what its row says. A step that is forbidden is recorded as failed and listed in section 7-1 of `report-details.md`; a check that reads a missing `objects/<kind>.json` or `metrics/<id>.json` reports `skip`. A summary or inventory check whose rule needs that input (`rule.needs`) reports `skip` as well, or `done` with the targets it could not judge named in section 7-5; it never passes on an empty input ([#114](https://github.com/KyungHwanKim-devs/kubegap/issues/114)).

`tests/test_permissions.py` keeps this file honest: the Kubernetes table must list exactly the ClusterRole's (group, resource) entries with their verbs, the AWS table exactly the policy's actions, every step named in a "Read by" or "Called by" cell must exist in `collectors/*/collect.yaml`, and the "Mode" cell must match the `modes:` of those steps. The check column is written by hand from the summary sections each kind feeds; `tests/test_permissions.py` also proves, in both directions, that the code reads nothing the role does not grant and the role grants nothing the code does not read.

Notation. `core/objects.dump-all` is step `objects.dump-all` of `collectors/core/collect.yaml`; it lists every resource kind the ClusterRole allows, once, and writes `objects/<kind>.json`, so almost every Kubernetes row names it. `lib/discover.py` reads a few kinds before collection to tell what the cluster is (platform, components, profile). Mode `both` means the step runs in `daily` and `full`; `full` means only there. For the README's view of the same facts see "Permissions used" in the modes table and "Run with the least access" in [README.md](../README.md).

The default `system:discovery` binding already grants these to every authenticated user; they are in the role so that the role reads complete on its own.

### Why `nodes/proxy` stays

One step uses it, `core/kubelet-configz`, full mode only, and three checks read what it returns: `node.kubelet-reserved-missing`, `node.kubelet-eviction-memory-missing` and `node.kubelet-api-qps-low`. The alternative source for the same facts is the kubelet configuration file on the node, which needs node access; GKE and AKS users without the DaemonSet backend have none. Remove the grant and exactly those three checks skip with "kubelet not read"; nothing else changes, and the failed step shows in section 7-1.

### CRDs

The role names 16 CRD groups (the rows from `monitoring.coreos.com` down). With this role a CRD outside them is not readable: `objects.dump-all` lists it among the kinds the API server offers, the LIST is forbidden, and the step records it under `not_permitted` (section 7-1 of `report-details.md` prints "Kinds the ClusterRole does not grant"). No check reads such a kind, so nothing is lost. With an administrator kubeconfig every listable kind is dumped. The README section "Run with the least access" says how to run with this role on a dedicated user.

### What is never read

- Secrets. The role has no `secrets` entry, `objects.dump-all` excludes the kind, and no `kubectl` call in the code asks for it (`tests/test_permissions.py` scans every call). Names and types come from the `kube_secret_info` metric of kube-state-metrics. The one exception is Helm: `helm list` (full mode, step `core/helm-list`) reads the release records Helm stores in Secrets, and kubegap keeps name, namespace, status, revision, chart and app version from them. Under this role `helm list` fails and the two Helm checks skip; grant `secrets` read only if you want them.
- ConfigMap values. `lib/scrub.py` drops every value at collection time except the keys in `KEEP_VALUES` (component configuration such as the CoreDNS Corefile and the kube-proxy config) and stores length and shape instead.
- Anything with a write verb. The role has `get`, `list` and the one `create` on `pods/portforward`; the IAM policy has Describe, List and Get actions plus `ssm:SendCommand` on one document. `tests/test_permissions.py` scans every `kubectl` and `aws` call in the code for verbs.

### Commands that reach a node

`ssm:SendCommand` is the EKS way in; on k3s and bare metal the same scripts go over SSH (`deploy/node-access/README.md`), and where neither exists through `kubectl exec` into the node-reader DaemonSet (`deploy/node-access/daemonset.yaml`, which needs `get` and `create` on `pods/exec` in the `kubegap` namespace from `deploy/permissions/role-daemonset-exec.yaml`). The `type: node` steps, all full mode only: `core/node-os` (every platform), `eks-platform/kubelet-journal` and `eks-platform/containerd-journal` (EKS), `k3s-platform/k3s-journal-errors`, `k3s-platform/k3s-journal-stats`, `k3s-platform/k3s-scheduler-unschedulable`, `k3s-platform/k3s-webhook-failures`, `k3s-platform/k3s-etcd-slow`, `k3s-platform/kubelet-pleg`, `k3s-platform/k3s-node` and `k3s-platform/containerd-log` (k3s), `kube-proxy/proxy-mode` (every platform), `vpc-cni/ipamd-metrics` (EKS). The pod-metrics fallback curl runs in both modes. Every command text, per backend, is in [`deploy/node-access/COMMANDS.md`](../deploy/node-access/COMMANDS.md).

### `ssm:SendCommand`, in detail

The policy allows `ssm:SendCommand` twice, and both statements must match for a command to go through: on the document `arn:aws:ssm:*:<ACCOUNT_ID>:document/kubegap-node-read` only, and on instances carrying the tag `kubernetes.io/cluster/<CLUSTER_NAME>=owned` only. So a key with this policy can run that one document, on that one cluster's nodes, and nothing else. The document is [`deploy/permissions/ssm-document.yaml`](../deploy/permissions/ssm-document.yaml): `step` selects one of a fixed list of read commands; the only other parameters are `podIp`, limited to an IPv4 address by `allowedPattern`, and `executionTimeout`, limited to digits. The commands are listed per backend in [`deploy/node-access/COMMANDS.md`](../deploy/node-access/COMMANDS.md); both files are generated from the collector definitions and a test fails when either is stale. Before sending, `lib/node.py` compares the sha256 of the local document with the one in the account and refuses to send when they differ. Uploading the document needs `ssm:CreateDocument`, `ssm:UpdateDocument`, `ssm:UpdateDocumentDefaultVersion` and `ssm:ListDocumentVersions` once, on your own credentials (`kubegap setup --install-ssm-document`); they are not in the audit policy.
