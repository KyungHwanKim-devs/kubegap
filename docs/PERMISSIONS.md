# Permissions, one by one

What each grant in [`deploy/permissions/clusterrole.yaml`](../deploy/permissions/clusterrole.yaml) and [`deploy/permissions/iam-policy.json`](../deploy/permissions/iam-policy.json) is used for: the collection step or library code that calls it, the mode in which that runs, the checks that need the result, and what happens when the grant is missing. A grant you remove costs what its row says. A step that is forbidden is recorded as failed and listed in section 7-1 of `report-details.md`; a check that reads a missing `objects/<kind>.json` or `metrics/<id>.json` reports `skip`. A summary or inventory check whose rule needs that input (`rule.needs`) reports `skip` as well, or `done` with the targets it could not judge named in section 7-5; it never passes on an empty input ([#114](https://github.com/KyungHwanKim-devs/kubegap/issues/114)).

`tests/test_permissions.py` keeps this file honest: the Kubernetes table must list exactly the ClusterRole's (group, resource) entries with their verbs, the AWS table exactly the policy's actions, every step named in a "Read by" or "Called by" cell must exist in `collectors/*/collect.yaml`, and the "Mode" cell must match the modes of the collection unit those steps belong to (`collectors/units.yaml`). The check column is written by hand from the summary sections each kind feeds; `tests/test_permissions.py` also proves, in both directions, that the code reads nothing the role does not grant and the role grants nothing the code does not read.

Notation. `core/objects.dump-all` is step `objects.dump-all` of `collectors/core/collect.yaml`; it lists every resource kind the ClusterRole allows, once, and writes `objects/<kind>.json`, so almost every Kubernetes row names it. `lib/collection/discover.py` reads a few kinds before collection to tell what the cluster is (platform, components, scale). Mode `both` means the step runs in `daily` and `full`; `full` means only there. The same facts by mode are in "What each mode uses" below, and the smallest set that still gives a report is in [`SETUP.md`](SETUP.md#run-with-the-least-access).

## The short version

kubegap never changes the cluster. It makes read calls only, and it uses the access your own kubeconfig, AWS profile and SSH already have. For a dedicated audit identity, these are the pieces:

- **Cluster.** [`deploy/permissions/clusterrole.yaml`](../deploy/permissions/clusterrole.yaml): `get` and `list` on the core resources and the API groups kubegap reads, Secrets excluded; `nodes/proxy` for the kubelet configuration; `pods/proxy` for a component pod's `/metrics` through the API server; and `create` on `pods/portforward`, which is how `kubectl port-forward` to Prometheus, Alertmanager, Loki and Grafana is authorized and creates nothing in the cluster. Every grant is one the code calls, and a test keeps it that way. Kinds of groups the role does not list are reported as not permitted, not as failures; no check reads them.
- **AWS, on EKS.** [`deploy/permissions/iam-policy.json`](../deploy/permissions/iam-policy.json): Describe, List and Get actions, CloudWatch `GetMetricData`, and SSM `SendCommand` limited in two ways. It may run only the document `kubegap-node-read`, which embeds the read commands and takes no free command text, and only on instances tagged `kubernetes.io/cluster/<CLUSTER_NAME>=owned`, the tag managed node groups and Karpenter already put on every node. The account id in the document ARN keeps a same-named document shared from another account from matching. `scripts/kubegap iam-policy --context <name>` prints the policy with `<ACCOUNT_ID>` and `<CLUSTER_NAME>` filled in from your kubeconfig; it prints only and sends nothing to AWS. Add `--without-node-access` for the policy without the two `SendCommand` statements.
- **Every command that reaches a node, on any backend.** [`deploy/node-access/COMMANDS.md`](../deploy/node-access/COMMANDS.md), generated from the collector definitions and kept current by a test.
- **Nodes over SSH, on k3s and bare metal.** [`deploy/node-access/README.md`](../deploy/node-access/README.md): one line to join the log-reading groups, optionally a sudoers file allowing read-only commands.
- **Nodes with neither SSM nor SSH, on GKE, AKS and other managed nodes.** Not read. The node checks are reported as not collected.

The one-time upload of the SSM document is not part of the audit policy. It runs with your own credentials and needs `ssm:CreateDocument`, `ssm:UpdateDocument`, `ssm:UpdateDocumentDefaultVersion` and `ssm:ListDocumentVersions`.

### What each mode uses

- **A daily run.** Kubernetes `get` and `list` on the resources in the ClusterRole; `pods/log` for the component logs, which a script counts in memory without writing them; port-forward to Prometheus, Alertmanager, Loki and Grafana; the Grafana API with `grafana_api_token` when one is set. A daily run calls no AWS API and contacts no node: every row of the AWS table below is a full run. The only AWS call left is the one the kubeconfig of an EKS cluster makes by itself, `aws eks get-token`.
- **A full run.** Everything a daily run uses, plus: on EKS the AWS Describe and List calls of discovery and setup (`eks`, `ecr:DescribeRepositories`, `ssm:DescribeInstanceInformation`, `ssm:DescribeDocument`, `sts`, `logs:DescribeLogGroups`) and the AWS steps (`alb-metrics` is `elasticloadbalancing:Describe*`, `ec2:DescribeSecurityGroups` and `cloudwatch:GetMetricData`); the node scripts and the node-side curl of the pod-metrics fallback (SSM `send-command` of the pinned document, or SSH); `nodes/proxy` for the kubelet configuration; CloudWatch Logs Insights (`logs:StartQuery`, `GetQueryResults`, `StopQuery`) and the quota and EBS `GetMetricData` queries; `helm list` (reads Helm's release Secrets, metadata only); cost and pricing, ECR, service quotas; and the external tools krr, polaris, pluto and kubent.

How to run with the least of all this, and what such a run cannot see, is in [`SETUP.md`](SETUP.md#run-with-the-least-access). What is collected, kept and sent is in [`DATA.md`](DATA.md).

The default `system:discovery` binding already grants these to every authenticated user; they are in the role so that the role reads complete on its own.

### Why `nodes/proxy` stays

One step uses it, `core/kubelet-configz`, full mode only, and three checks read what it returns: `node.kubelet-reserved-missing`, `node.kubelet-eviction-memory-missing` and `node.kubelet-api-qps-low`. The alternative source for the same facts is the kubelet configuration file on the node, which needs node access; GKE and AKS users have none. Remove the grant and exactly those three checks skip with "kubelet not read"; nothing else changes, and the failed step shows in section 7-1.

### CRDs

The role names 16 CRD groups (the rows from `monitoring.coreos.com` down). With this role a CRD outside them is not readable: `objects.dump-all` lists it among the kinds the API server offers, the LIST is forbidden, and the step records it under `not_permitted` (section 7-1 of `report-details.md` prints "Kinds the ClusterRole does not grant"). No check reads such a kind, so nothing is lost. With an administrator kubeconfig every listable kind is dumped. "Run with the least access" in [`SETUP.md`](SETUP.md#run-with-the-least-access) says how to run with this role on a dedicated user.

### What is never read

- Secrets. The role has no `secrets` entry, `objects.dump-all` excludes the kind, and no `kubectl` call in the code asks for it (`tests/test_permissions.py` scans every call). Names and types come from the `kube_secret_info` metric of kube-state-metrics. The one exception is Helm: `helm list` (full mode, step `core/helm-list`) reads the release records Helm stores in Secrets, and kubegap keeps name, namespace, status, revision, chart and app version from them. Under this role `helm list` fails and the two Helm checks skip; grant `secrets` read only if you want them. pluto never reaches the cluster, whatever the identity may read: its in-cluster modes List every resource the server advertises, Secrets included, so the step gives it the `apiVersion`, kind, name and namespace of the saved objects on stdin (`lib/foundations/lastapplied.py`). kubent Lists a fixed set of 41 kinds with no Secret among them.
- ConfigMap values. `lib/foundations/scrub.py` drops every value at collection time except the keys in `KEEP_VALUES` (component configuration such as the CoreDNS Corefile and the kube-proxy config) and stores length and shape instead.
- Anything with a write verb. The role has `get`, `list` and the one `create` on `pods/portforward`; the IAM policy has Describe, List and Get actions plus `ssm:SendCommand` on one document. `tests/test_permissions.py` scans every `kubectl` and `aws` call in the code for verbs.

### Without any IAM permission (#22)

Many people want to try an EKS audit before security approves the IAM policy. There is no run "without AWS credentials": the kubeconfig of an EKS cluster authenticates with `aws eks get-token`, so some AWS identity is always there. The case that exists is an identity that may read the cluster (an access entry or `aws-auth` mapping bound to `deploy/permissions/clusterrole.yaml`) and holds no IAM policy. Measured on 2026-11-06 on the maintainer's cluster (EKS 1.32, 8 nodes, the `prod` profile) with an IAM role that has exactly that and nothing else: every AWS call but `sts get-caller-identity` is refused with `AccessDenied`, `kubegap setup` prints the refusals in its AWS block, and collection, summary and evaluation run to the end.

| Mode | Checks | Evaluated | Skipped for the missing IAM permissions | Skipped for other reasons | Not collected in this mode |
|---|---|---|---|---|---|
| daily | — | — | 0 | — | — |
| full | 365 | 295 | 57 | 6 (the same four, plus the two Helm checks, which the shipped ClusterRole stops because `helm list` reads Secrets) | 0 |

The daily row was measured when a daily run still called AWS. Since the daily run stopped calling AWS (it reads the Kubernetes API and the stores only), a missing IAM policy changes nothing in it, and the checks that need AWS are listed as not collected in this mode.

The remaining four checks of each row are the two that do not run on this platform and the two LLM checks. The three tools missing on the test machine (krr, polaris) are left out.

What the missing permissions take away, each reported as skipped with its reason, never as a pass:

- the 23 `node.*` checks that read the node scripts and the kubelet configuration (SSM `send-command` is refused; the ten node checks that read Prometheus keep running), and `eks.ssm-unregistered`;
- the eleven EKS checks that read `describe-cluster` and what follows from it: `eks.audit-log-off`, `eks.public-endpoint-open`, `eks.node-os-skew`, `eks.extended-support`, `eks.no-backup-policy`, `eks.addon-outdated`, `eks.nodegroup-ami-old`, `eks.security-group-open-to-world`, `eks.acm-certificate-expiring`, `eks.service-quota-near-limit`, and `vpccni.external-snat-off-with-private-routes`;
- the eight `ecr.*` checks and the four `storage.ebs-*` checks;
- the pod `/metrics` read through the node when the API server proxy is blocked, which on this cluster is what `albctl.aws-api-churn`, `albctl.reconcile-errors`, `argocd.backend-errors`, `eso.provider-api-errors`, `karpenter.consistency-errors`, `karpenter.nodepool-usage-near-limit`, `keda.external-metrics-api-errors`, `vpccni.ec2-api-errors`, `grafana.alerting-failures` and `grafana.datasource-errors` read; `*.metrics-unreadable` warns in their place;
- in full mode also the Logs Insights queries behind the control-plane log checks and the seven `cost.*` checks' AWS inputs. Of the six control-plane log checks, `controlplane.etcd-slow` is disabled in `prod`, `controlplane.scheduler-unschedulable`, `controlplane.webhook-call-failures` and `controlplane.controller-error-repeat` evaluate to an empty count, and `controlplane.apiserver-slow-traces` and `controlplane.authenticator-failures` skip ("control plane logs not read").

Two things to know when reading such a report. First, `describe-cluster` is the call discovery builds on: refused, the inventory keeps the cluster name, region and account and nothing else, so the steps that take the VPC id, the subnet ids, the node groups or the add-ons from it (`subnets`, `cluster-security-groups`, `route-tables`, `cluster-versions`, `nodegroup`, `addon-versions`, `ecr/images`, `ecr/lifecycle-policy`) report an empty input ("list is empty", "placeholder has no value in the inventory") rather than the refusal; `run.log` and the `setup` output hold the refusal itself. Second, a check whose AWS input was refused skips and says which call: `cost.idle-compute-high` and `cost.request-waste` (pricing), `cost.unused-eip` (`ec2:DescribeAddresses`), `cost.idle-load-balancer` (`elasticloadbalancing:Describe*`), `security.imds-hop-limit` (`ec2:DescribeInstances`), `controlplane.apiserver-slow-traces` and `controlplane.authenticator-failures` (Logs Insights); the summary section each reads carries a `*_read` flag or is `null` with a `skip_reason`, and the rule's `needs` reads it (#141). `cost.on-demand-in-spot-pool` reads node labels and NodePools, not AWS, so it judges as before.

### Commands that reach a node

`ssm:SendCommand` is the EKS way in; on k3s and bare metal the same scripts go over SSH (`deploy/node-access/README.md`); where neither exists the nodes are not read. The `type: node` steps, all full mode only: `core/node-os` (every platform), `eks-platform/kubelet-journal` and `eks-platform/containerd-journal` (EKS), `k3s-platform/k3s-journal-errors`, `k3s-platform/k3s-journal-stats`, `k3s-platform/k3s-scheduler-unschedulable`, `k3s-platform/k3s-webhook-failures`, `k3s-platform/k3s-etcd-slow`, `k3s-platform/kubelet-pleg`, `k3s-platform/k3s-node` and `k3s-platform/containerd-log` (k3s), `kube-proxy/proxy-mode` (every platform), `vpc-cni/ipamd-metrics` and `vpc-cni/ipamd-log` (EKS). The pod-metrics fallback curl runs in both modes. Every command text, per backend, is in [`deploy/node-access/COMMANDS.md`](../deploy/node-access/COMMANDS.md).

### `ssm:SendCommand`, in detail

The policy allows `ssm:SendCommand` twice, and both statements must match for a command to go through: on the document `arn:aws:ssm:*:<ACCOUNT_ID>:document/kubegap-node-read` only, and on instances carrying the tag `kubernetes.io/cluster/<CLUSTER_NAME>=owned` only. So a key with this policy can run that one document, on that one cluster's nodes, and nothing else. The document is [`deploy/permissions/ssm-document.yaml`](../deploy/permissions/ssm-document.yaml): `step` selects one of a fixed list of read commands; the only other parameters are `podIp`, limited to an IPv4 address by `allowedPattern`, and `executionTimeout`, limited to digits. The commands are listed per backend in [`deploy/node-access/COMMANDS.md`](../deploy/node-access/COMMANDS.md); both files are generated from the collector definitions and a test fails when either is stale. Before sending, `lib/collection/node.py` compares the sha256 of the local document with the one in the account and refuses to send when they differ. Uploading the document needs `ssm:CreateDocument`, `ssm:UpdateDocument`, `ssm:UpdateDocumentDefaultVersion` and `ssm:ListDocumentVersions` once, on your own credentials (`kubegap setup --install-ssm-document`); they are not in the audit policy.
